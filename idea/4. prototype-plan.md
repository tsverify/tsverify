## 1. Goal

Prove the core loop end to end on a realistic demo app:

> An agent writes **code + `*.behavior.yaml`**. `tsv` **renders** the spec for a human, **model-checks** the spec, **extracts** the code's actual behavior, **diffs** the two, and turns every violation into a **failing test**. CI reads the exit code.

### Success criteria

| # | Criterion |
|---|---|
| S1 | All 6 seeded bugs in the demo app are detected and classified correctly (§7) |
| S2 | The two concurrency bugs (B3, B4) are **confirmed by generated replay tests that fail** against the real code |
| S3 | The bug-free demo variant produces **zero findings** and exit code `0` |
| S4 | `tsv check` on the demo app takes < 5s. `tsv test` (generate + run) takes < 20s |
| S5 | `tsv view` shows the diagram, the permission matrix, and counterexample playback |
| S6 | `tsv diff` produces a PR-ready Markdown comment with a Mermaid behavior diff |
| S7 | Runs with `npx`/`pnpm dlx`: **no JVM, no database, no network, no cloud**. Needs only install + `*.behavior.yaml` (doc 3, D7). All analysis state is in memory |
| S8 | Meets the performance budgets in [doc 5 §5](./5.%20language-and-performance.md), including on one ~200k-LOC open-source repo |

## 2. Tech stack

| Concern | Choice | Why |
|---|---|---|
| Language/runtime | TypeScript, Node ≥ 20 | Same ecosystem as the users. Node 20+ provides `AsyncLocalStorage`, needed by the replay scheduler |
| Monorepo | pnpm workspaces | Standard for multi-package open-source TypeScript projects |
| YAML | `yaml` (eemeli) | Keeps source positions, so errors point to `file:line:col` |
| Schema | zod v4 → JSON Schema | One definition gives runtime validation **and** the published JSON Schema that editors and agents use |
| Code analysis | ts-morph (TypeScript compiler API), behind a `TypeFacts` interface | Type checker (narrowing), AST, symbol resolution. A TS 7.1 native API backend can be swapped in later (doc 5) |
| Tests (ours and generated) | vitest | Module mocking (`vi.mock`) for replay. Fast |
| CLI | `cac` + `picocolors` | Small and dependency-light |
| Viewer | Vite-built static SPA (Preact) + Mermaid, served by a tiny Node server with file watching | Reuses the same Mermaid output as PR comments. Switch to custom SVG/elkjs only if playback needs it |
| Model checking | **Built-in explicit-state checker** (TypeScript, integer-encoded states, symmetry reduction; a pure module over the IR so it can be ported to Rust later; see doc 5) | Entity models are small. This gives millisecond runs, exact counterexamples, and zero install. Counterexamples are emitted as **ITF JSON** (the Quint/Apalache trace format) for interop |

## 4. Core data model: one IR for spec and code

The spec and the extracted code produce **the same type**, so conformance is a model diff and the checker runs on both.

```ts
// packages/ir
export type Origin = { kind: "spec"; file: string; line: number; col: number }
                   | { kind: "code"; file: string; line: number; col: number };

export interface BehaviorModel {
  kind: "entity";                         // later: "function" | "flow" | "system" | "policy"
  name: string;
  origin: "spec" | "code";
  entity: { name: string; stateField: string; states: string[]; initial: string; terminal: string[] };
  actors: Record<string, Actor>;
  transitions: Transition[];
  rules: Rule[];
  concurrency: Record<string, number>;    // max parallel invocations per transition
}

export interface Transition {
  name: string;
  from: string[] | "*";                   // "*" = unconstrained (extractor couldn't narrow)
  to: string;
  by: string[];
  requires: GuardRef[];
  effects: { name: string; multiplicity: "exactly-once" | "at-least-once" | "idempotent" }[];
  atomic: boolean;
  idempotent: boolean;
  after?: string;
  impl?: { file: string; symbol: string };
  at: Origin;
  // extractor-only detail, used by replay to map model steps → code call sites
  sites?: { read?: Origin; write?: Origin; guards?: Origin[]; effects?: Origin[] };
}
```

## 5. Checker semantics (MVP)

**State:** `{ status, effectCounts, workers[] }`. Each worker is one in-flight invocation of a transition, up to `concurrency[t]`. The default is **2**, so races are explored by default.

**Steps per transition:**
- `atomic: true` → **one step**: enabled if `status ∈ from`. Sets `status := to` and increments the effect counts.
- `atomic: false` → **two steps**:
  - `read`: the worker observes `status` and proceeds only if it is in `from`.
  - `write`: sets `status := to` and increments the effects **without re-checking**. This is the check-then-act gap.
- `idempotent: true` → the triggering event may be **delivered twice** (duplicate delivery).

**Built-in properties (always checked):**

| Property | Meaning | Kind |
|---|---|---|
| `reachable` | Every declared state is reachable | warning |
| `no-stuck-states` | From every reachable state, a terminal state is still reachable (AG EF terminal) | error |
| `effect-multiplicity` | An `exactly-once` effect fires at most once per entity in every reachable state | error |
| `untrusted-guarded` | Every transition by an `untrusted` actor has a `requires` guard | error (lint) |
| `webhook-idempotent` | Transitions by `signed-webhook` actors must be `idempotent` | error (lint) |

**Rules, a mini expression language:**

```
always:     <expr>                          # invariant (checked on every reachable state)
never:      <expr>                          # sugar for always: not <expr>
eventually: <expr>                          # MVP meaning: "from every reachable state, <expr> is reachable"
                                            #   (AG EF). Weaker than LTL-with-fairness; documented.
<expr> := status == s | status in [s,…] | count(effect NAME) <op> n
        | <expr> and/or <expr> | not <expr> | <expr> implies <expr> | ( <expr> )
```

**Algorithm:** BFS with a visited set gives the shortest counterexamples. A parent-pointer trace is emitted as ITF JSON plus a human-readable step list.

## 6. CLI surface (prototype)

```
tsv validate [paths…]            schema + impl-link validation                  exit 0 | 2
tsv check    [paths…]            spec model check + extraction + conformance    exit 0 | 1 | 2 | 3
             [--spec-only] [--format pretty|json|sarif] [--scope entity]
tsv test     [paths…]            generate tests into .tsv/generated/ and run them via vitest
tsv render   <spec> --mermaid | --matrix | --summary
tsv view     [paths…]            local interactive viewer with live reload
tsv diff     --base <git-ref>    behavior diff (Markdown + Mermaid) for PR comments
tsv schema                       print JSON Schema (for yaml-language-server / agents)
```

Discovery: `**/*.behavior.yaml`. Bindings (persistence, clients, guards) live in each spec's `bindings:` section. An optional root `tsv.config.yaml` can provide shared defaults (doc 3, Part B and D7).

## 7. Demo app: `examples/orders-app`

A small order and payments service using the **repository + plain assignment** pattern, with in-memory stores and fake Stripe/email clients. Its `order.behavior.yaml` is the example from doc 2.

| Variant | Seeded bug | Expected detection |
|---|---|---|
| `clean` | none | exit 0, zero findings |
| **B1** | Admin "reopen" sets `paid → pending_payment` | extractor: **undeclared transition** |
| **B2** | `refund` has an early-return branch that skips `requireRole` | extractor: **guard doesn't dominate the write** |
| **B3** | `refund` reads, awaits Stripe, then writes (non-atomic) | extractor: **atomicity**. As-implemented model: double refund. **Replay test fails** |
| **B4** | `payment_succeeded` webhook sends a receipt email without checking whether the order is already paid | checker on as-implemented model: duplicate delivery → `email.send ×2`. **Replay test fails** |
| **B5** | `cancel` calls `stripe.refunds.create`, which the spec doesn't declare | extractor: **undeclared effect** |
| **B6** | *(Spec bug)* `refund` is missing `atomic: true` while the rule says "refund at most once" | checker on the **spec**: design-level counterexample, found before the code is involved |

Variants live as separate small directories (or as overlay patches applied by the e2e test). Each one doubles as an end-to-end test of `tsv`.

## 8. Milestones

Sizes: **S** ≈ small, **M** ≈ medium, **L** ≈ large. The **prototype** is M0–M6, which proves the loop. The **public alpha** is M7–M10, which is releasable.

### Risk spikes (do first, in parallel with M1)

| Spike | Question to answer | Exit criterion |
|---|---|---|
| **X1 Narrowing** (S) | Can ts-morph give the **narrowed literal-union type** of `entity.status` at an arbitrary write site? | Fixture with 5 guard styles (`if/throw`, `switch`, early return, `assert`, ternary): correct from-sets for all |
| **X2 Gating** (M) | Can `vi.mock` + `AsyncLocalStorage` + gates force a specific interleaving of real async code? | A replay of the B3 race fails deterministically 100/100 runs, and the fixed code passes 100/100 |

### Prototype

| M | Deliverable | Acceptance |
|---|---|---|
| **M0** (S) | Scaffold: pnpm workspace, TS config, vitest, lint/format, CI workflow, LICENSE, README stub | `pnpm test` is green in CI |
| **M1** (M) | `spec` + `ir`: zod schema, YAML loader with positions, validation messages, normalization to IR, `tsv validate`, `tsv schema` | Golden tests. Invalid specs → `file:line` errors and exit 2 |
| **M2** (M) | `checker`: explicit-state BFS, built-ins, rule language, ITF and pretty counterexamples, `tsv check --spec-only` | B6 is caught. The clean spec passes. Golden traces |
| **M3** (S) | `render`: Mermaid state diagram, permission matrix, summary, `tsv render` | Snapshot tests. The output renders on GitHub |
| **M4** (M) | `examples/orders-app`: clean version + B1–B5 variants + spec | The app's own tests pass on `clean` |

## 9. How we test `tsv` itself

- **Unit tests** per package.
- **Golden files:** spec → IR, IR → Mermaid, checker → traces, `check --format json` output.
- **Extractor fixtures:** tiny TypeScript projects in `fixtures/`, each covering one pattern (guard styles, aliasing, helper functions, early returns).
- **End-to-end:** every demo variant runs `tsv check` and `tsv test`, and the expected findings and exit codes are asserted. This **is** the success-criteria suite (§1).

# 5. Implementation Language and Performance

> Status: v0.5 · Question: is TypeScript fast enough, or should `tsv` be built in Rust?
> Decision: **TypeScript core with one isolated hot path (the model checker) that can be ported to Rust later.** Reasoning below.

---

## 1. Where the time actually goes

| Component | Work | Expected cost | Language-sensitive? |
|---|---|---|---|
| YAML load + validate | Parse a few small files | ms | No |
| **Extractor** | **Type-check the user's project** with the TypeScript type checker, then walk the ASTs of the `impl` functions | **seconds to tens of seconds on big repos.** Nearly all of it is the type checker | **Only through which type checker we call** (see §2) |
| Conformance diff | Compare two small models | ms | No |
| **Model checker** | Explore every reachable state (BFS) | ms at entity scope; **could reach millions of states at flow scope** | **Yes. This is the real hot path** |
| Generated tests | vitest runs the user's real code | seconds | No (it's the user's code) |
| Viewer / render | Browser + Mermaid | n/a | No |

**Conclusion:** writing `tsv` in Rust would not speed up the dominant cost, which is type-checking the user's code. Only the model checker is a CPU-bound workload where the implementation language matters.

---

## 2. The deciding constraint: type information

The extractor's key trick (doc 3, Part B) is asking TypeScript's own type checker what `order.status` narrows to at a write site. That requires a **full TypeScript type checker**:

| Option | Status (Nov 2026) | Usable from |
|---|---|---|
| TypeScript 5.x/6.x (JS compiler, via **ts-morph**) | Mature. Full programmatic API | **Node/TypeScript only** |
| **TypeScript 7 (native Go port)** | Stable since July 2026, ~8–12× faster builds. **Full programmatic API slated for 7.1** | Node via API (7.1+); IPC from other languages |
| Rust TypeScript type checkers (stc, ezno) | Abandoned or experimental. Not viable | Rust |
| Rust parsers (oxc, swc) | Excellent and very fast, but **parse only, with no type checking** | Rust |

So a Rust `tsv` would have to either:
- **drop type-aware analysis** and guess from syntax, which means losing from-state narrowing, losing ORM model types, and getting more false positives; or
- **call out to the TypeScript type checker anyway** (a Node subprocess or the TS 7 IPC API). That adds a second runtime and a serialization boundary, and still pays the type-checking cost.

The Rust lint ecosystem points the same way: Rust-native linters stay fast by skipping type information. When they add type-aware rules, they **delegate to the TypeScript 7 native checker** rather than reimplementing it.

---

## 3. Pros and cons

### TypeScript

| Pros | Cons |
|---|---|
| Direct, in-process access to the TypeScript type checker (ts-morph now, TS 7.1 API later) | Model checker is ~3–10× slower than Rust for large state spaces (estimate) |
| Same language as the users. **Open-source contributors are TypeScript developers**, which lowers the barrier a lot | Node startup (~100–200 ms) on every CLI call |
| The parts that *must* be TypeScript (`@tsv/runtime`, generated tests, viewer) share types and code with the core: one language, one build | Memory per state is higher (JS objects); this needs compact encoding |
| `npx` install, and every user already has Node | Single-threaded by default; parallelism needs worker threads |
| Fastest iteration for a prototype whose design is still moving | |

### Rust

| Pros | Cons |
|---|---|
| Fastest model checker: compact states, multithreaded BFS, low memory | **No TypeScript type checker**, so type-aware extraction is lost or needs a Node/TS 7 bridge anyway |
| Single static binary with fast startup | Two languages regardless: runtime, generated tests and viewer stay TypeScript |
| Strong correctness guarantees in the tool's own code | Smaller contributor pool for a tool aimed at TypeScript developers |
| | Slower iteration while the design and IR are still changing |
| | Distribution via npm needs per-platform prebuilt binaries (manageable, but extra CI work) |

*(Go, briefly: TS 7 is written in Go, but its internals aren't a public Go library. A Go `tsv` would still go through the same external API, so it has the same trade-off as Rust.)*

---

## 4. Decision

1. **Build `tsv` in TypeScript.**
2. **Put the extractor behind a `TypeFacts` interface** (narrowed type at a node, resolved symbol, call targets). Implement it with ts-morph on TS 6 first, and add a **TS 7.1 native API backend** when that API ships. That gives the ~10× type-checking speedup without rewriting `tsv`.
3. **Keep the model checker a pure module over the IR**, with no dependency on the TypeScript compiler. If profiling shows it's needed, port it to **Rust compiled to N-API or WASM**, shipped as an optional native package with the TypeScript implementation as fallback. This is a well-defined seam: IR in, results and counterexamples out.
4. **Design the checker for speed from day one**, whatever the language:
   - **Integer-encoded states:** pack status, worker program counters and effect counts into a small number or typed array, and hash that.
   - **Symmetry reduction:** concurrent workers running the same transition are interchangeable, so store them as counts rather than ordered lists. This shrinks the state space dramatically.
   - **Bounds from the spec:** apply `concurrency` per transition, rather than to every transition.
   - **Partial-order reduction** later, if flow-scope models grow.

## 5. Performance budgets (added to the prototype plan)

| Budget | Target | Measured on |
|---|---|---|
| `tsv validate` | < 300 ms | demo app |
| `tsv check --spec-only` | < 500 ms | demo app |
| `tsv check` (full, cold) | < 5 s | demo app |
| `tsv check` (full, cold) | < 30 s | a ~200k-LOC open-source TypeScript repo (only files reachable from `impl` symbols are analyzed) |
| Checker throughput | ≥ 500k states/s | synthetic entity model |

If the checker misses its throughput budget on realistic flow-scope models, that triggers the Rust port in point 3 of §4. No other component is expected to need one.

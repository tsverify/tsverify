## Part A: Decisions recorded

| # | Decision | Notes |
|---|---|---|
| D1 | **Released as open source tooling** | Needs a license and a name before the first publish (see open items) |
| D2 | **No `tsv infer` on day one** | Agents generate as-is specs from existing code. The tool's job is to give them a **JSON Schema + an authoring guide**, then verify what they wrote: `tsv check` runs the extractor against the agent's spec. So an inferred spec is still checked, without a separate inference engine |
| D3 | **YAML** is the spec format | Parsed with position info, so every error points to a `file:line` |
| D4 | **The tool never decides policy; CI does** | Fixed exit codes plus machine-readable output. The README documents recommended workflows (advisory, blocking, blocking only for `enforced` specs) |
| D5 | **Local interactive viewer + Mermaid in PRs** | Same render core for both |
| D6 | **Multiple scope levels**, like unit/integration tests | See Part D. The prototype covers the **entity** scope end to end |
| D7 | **Local-only, zero setup** | Requirements are install + `*.behavior.yaml` files. No database, no network, no cloud, no services. See below |

### D7: Local-only runtime

"State" means two different things here, and `tsv` doesn't connect to either:

| What | Where it lives | How `tsv` deals with it |
|---|---|---|
| **The app's state** (e.g. `Order.status` in the user's Postgres) | The user's database, in production | `tsv` **never connects**. It only reads **source code**. "Prisma adapter" means "recognizes Prisma *call patterns* in the TypeScript", not "talks to the database" |
| **Model-checking state** (every reachable combination of status, workers and effect counts) | **In memory**, for the duration of one run | Built by the checker and discarded when the run ends |
| **Replay/generated tests** | In memory | Database and effect clients are replaced by **in-memory fakes** that implement the subset of the Prisma/Drizzle API used, including conditional `updateMany` semantics. No SQLite, no containers |
| **Cache** *(optional, later)* | Local files in `.tsv/cache/`, keyed by content hash | Purely a speed-up. Safe to delete; `--no-cache` disables it |

Practical consequences:
- `tsv test` runs generated tests with a **bundled vitest**, so the target project doesn't have to use vitest.
- Prisma types come from the generated client (`prisma generate`), which is already part of any Prisma project's normal development setup. If it's missing, `tsv` falls back to **parsing `schema.prisma`** for the enum values. That is also just reading a file.
- Drizzle schemas are plain TypeScript, so there is nothing extra to read.
- Anything `tsv` writes goes into `.tsv/` (generated tests, counterexamples, cache), which can be gitignored.

**Exit code contract (D4):**

| Code | Meaning |
|---|---|
| `0` | All checks passed |
| `1` | Violations found (behavior bugs or conformance mismatches) |
| `2` | Invalid input: spec doesn't parse or validate, broken `impl` link, bad config/CLI usage |
| `3` | Tool/internal error (crash, missing optional backend) |

Output formats: `--format pretty` (default for a TTY), `json`, `sarif` (GitHub code scanning). Filters such as `--scope entity` and `--spec path/to/file` let teams split runs the way they split test suites.

## Part B: What is the MVP extractor, and where do Prisma and Drizzle fit?

### What the extractor is

The extractor is the half of `tsv check` that **reads the TypeScript code and reconstructs the behavior it actually implements**, in the same shape as a behavior spec. For each transition's `impl` function it answers:

1. **Which state does it write?** For example, `status ← "refunded"`.
2. **From which states can that write happen?** This is the from-state.
3. **Which guard checks always run before the write?** For example, `requireRole("admin")`.
4. **Which external effects does it trigger?** For example, `stripe.refunds.create`.
5. **Are the read of the state and the write of the state atomic?**

The output is an **"as-implemented" model**. Conformance is then just a **diff between two models**: the spec and the code. A second benefit is that the model checker can run on the as-implemented model too, which is how code-level bugs get concrete counterexamples (Part C).

The core is built on the TypeScript compiler API through ts-morph. It needs:
- the call graph, to follow `impl` into the helpers it calls
- control-flow graphs, for "does the guard run on every path before the write" (dominance)
- the **type checker**, for from-state inference via narrowing (below)

### Where Prisma and Drizzle come in

The state usually lives in a **database**. Code changes it through a database library, and each library writes in a different syntax. The extractor needs to recognize "this line writes `Order.status`" in each of them. That recognition is the job of a **persistence adapter**, which is a small plugin:

| Pattern | What the code looks like | What the adapter extracts |
|---|---|---|
| **Plain assignment** (domain objects, in-memory) | `order.status = "refunded"; await repo.save(order)` | write `refunded`; from-state from narrowing |
| **Prisma** | `prisma.order.update({ where: { id }, data: { status: "refunded" } })` | write `refunded`, **not conditional**: the read and write are separate, so not atomic |
| **Prisma, conditional** | `prisma.order.updateMany({ where: { id, status: "paid" }, data: { status: "refunded" } })` | write `refunded` from `paid`, **atomic** (the database checks and writes in one statement) |
| **Drizzle** | `db.update(orders).set({ status: "refunded" }).where(and(eq(orders.id, id), eq(orders.status, "paid")))` | same as Prisma conditional, but a different call shape (builder chain instead of an object literal) |
| **Transactions** | `prisma.$transaction(async tx => …)` / `db.transaction(async tx => …)` | marks the read and write inside as atomic (depending on isolation level; documented caveat) |
| **Raw SQL** *(later)* | ``sql`UPDATE orders SET status = 'refunded' WHERE …` `` | best-effort parse of the template string |

Each adapter implements one interface:

```ts
interface PersistenceAdapter {
  name: string;                                        // "assign" | "prisma" | "drizzle" | …
  matchStateWrite(call: Node, ctx): StateWrite | null; // entity, field, value, condition, site
  matchStateRead(call: Node, ctx): StateRead | null;   // used for check-then-act detection
  matchAtomicScope(node: Node, ctx): AtomicScope | null; // transactions / locks
}
```

### How the from-state is inferred (the key trick)

```ts
const order = await prisma.order.findUniqueOrThrow({ where: { id } });  // read
if (order.status !== "paid") throw new NotRefundable();
// ← here TypeScript narrows order.status to "paid"
await stripe.refunds.create({ charge: order.chargeId });
await prisma.order.update({ where: { id }, data: { status: "refunded" } }); // write
```

Prisma enums and Drizzle `pgEnum` / `text({ enum })` both generate **TypeScript literal unions**. The type checker already knows that `order.status` is `"paid"` at the write site. So the from-state is `{paid}`, at no cost, with no custom data-flow analysis. If the type is just `string`, the from-state is `*` (any), which gets flagged as over-permissive.

The same snippet also shows why the **atomicity check** exists. Narrowing describes the value that *was read*, not the database at the moment of the write. There are two separate `await`s between the read and the write, so another request can slip in between them. That gap is exactly the double-refund race.

### Which adapters ship first

1. **`assign`** first. It has zero dependencies, so it proves the core analysis (narrowing, dominance, effects, atomicity) without any ORM. The demo app starts on a repository pattern.
2. **`prisma`** second. It is the most widely used TypeScript ORM, its generated client is strongly typed (so we know `prisma.order` is the `Order` model and `status` is an enum union), and its calls are regular object literals.
3. **`drizzle`** third. It proves the adapter interface works for a builder-style API.

A `bindings:` section in the behavior YAML tells the extractor what it can't guess. No separate config file is required (see D7):

```yaml
# inside order.behavior.yaml
bindings:
  persistence: prisma          # optional: auto-detected from @prisma/client / drizzle-orm imports
  clients:
    db:     { module: src/db.ts, export: prisma }      # also used by generated tests to intercept
    stripe: { module: src/payments/stripe.ts, export: stripe }
  guards:
    role(admin): src/auth/guards.ts#requireRole("admin")
    owner:       src/auth/guards.ts#requireOwner
```

An optional `tsv.config.yaml` at the repo root can hold the same `bindings` as shared defaults, so they aren't repeated in every spec. It is never required.

## Part C: What do "counterexample", "playback", and "replay" mean?

**Counterexample.** When the model checker finds a rule that can be broken, it doesn't just say "fails". It returns the **exact sequence of steps** that breaks it:

```
state 0  status=paid  refunds=0
step 1   w1: refund.read     (w1 sees status=paid)
step 2   w2: refund.read     (w2 sees status=paid)
step 3   w1: refund.write    → stripe.refund, status=refunded   refunds=1
step 4   w2: refund.write    → stripe.refund, status=refunded   refunds=2  ✗ "Refund issued at most once"
```

That trace is the counterexample. There are two ways to use it.

### Playback (visual, for humans)

In the **local viewer**, the counterexample becomes a timeline you can step through:
- The state diagram highlights the current state at each step.
- A swimlane per worker or actor shows who did what, and when.
- Effects light up as they fire (💳 ×1, then 💳 ×2 ✗).
- The violated rule is shown at the failing step.

This works **at the spec level**, so it helps even before any code exists. For example, it shows a designer why `refund` must be `atomic`.

### Replay (executable, for agents and CI)

`tsv` **generates a real TypeScript test** that forces the actual code through the same steps in the same order. If the test fails, the bug is **confirmed in the real code**, not just in the model.

The hard part is forcing an interleaving of async code. The generated test:
1. Mocks the configured client modules (`clients.db`, `clients.stripe`) with instrumented versions. Vitest module mocking means no production code changes.
2. Each call on those clients waits at a **gate** controlled by a scheduler. `AsyncLocalStorage` tells the gate which worker is calling.
3. The scheduler releases the gates in the counterexample's order.

```ts
// .tsv/generated/order.refund.cex-1.test.ts   (generated: do not edit)
import { test, expect, vi } from "vitest";
import { scheduler, instrument } from "@tsv/runtime";

const s = scheduler();
vi.mock("../../src/db.ts", () => instrument.prisma(s, { Order: [{ id: "o1", status: "paid", chargeId: "ch_1" }] }));
vi.mock("../../src/payments/stripe.ts", () => instrument.effects(s, ["stripe.refunds.create"]));

const { refundOrder } = await import("../../src/orders/refund.ts");

test("Order.refund · rule 'Refund issued at most once' · 2 workers", async () => {
  s.spawn("w1", () => refundOrder("o1", s.actor("admin")));
  s.spawn("w2", () => refundOrder("o1", s.actor("admin")));

  await s.play([
    ["w1", "read Order"],
    ["w2", "read Order"],
    ["w1", "until-done"],
    ["w2", "until-done"],
  ]);

  expect(s.effects("stripe.refunds.create")).toHaveLength(1);   // fails: 2 calls → bug confirmed
});
```

The step-to-code mapping (`refund.read` ↔ `prisma.order.findUniqueOrThrow`) comes from the extractor, which already knows the read and write call sites.

### How the outcomes combine

| Spec model | As-implemented model | Replay test | Meaning |
|---|---|---|---|
| ✔ | ✔ | n/a | Conforms. Done |
| ✗ | n/a | n/a | **Design bug.** The spec itself is wrong. Fix the spec before (or while) coding. Playback explains it |
| ✔ | ✗ | **fails** | **Implementation bug, confirmed.** The code breaks a rule the spec guarantees (e.g. spec says `atomic`, code isn't) |
| ✔ | ✗ | passes | **Extractor or replay disagreement.** The code may be safer than it looked, or the instrumentation missed something. Reported as a warning with details, never silently dropped |

## Part D: Scope levels

Like tests, behavior specs come in layers. Higher layers **reference** lower ones (`uses:`) and never redefine them, so each fact lives in exactly one place. Every spec declares its `kind:`.

| Scope | Like… | Question it answers | Main engine | Code-conformance check | Typical speed |
|---|---|---|---|---|---|
| **function** | unit tests | "Does `refundAmount` respect its contract?" | Property tests generated from `ensures` (fast-check). SMT/Lean later | Link and signature check; generated property tests run the real function | ms–s |
| **entity** ← *prototype* | component tests | "Can an Order move only along allowed transitions, guarded, with effects at the right multiplicity, under concurrency?" | Explicit-state model checker (built in) | Extractor diff + path / forbidden / guard tests + replay | s |
| **flow** | integration tests | "Does checkout reserve stock, create the order and start payment in order, and undo correctly on failure?" | Composed entity models + step sequencing + failure injection | Call order on the handler's CFG; generated integration tests with per-step fault injection | s–min |
| **system** | end-to-end / chaos | "With at-least-once webhooks, reordering and crashes, does every paid payment end with a paid order?" | Model checking with environment nondeterminism: **Quint → Apalache / TLA+** | Per-service links, idempotency of consumers; later, trace validation against OpenTelemetry traces | min |
| **policy** *(cross-cutting)* | lint rules | "Is every transition by an untrusted actor guarded? Is every query tenant-scoped?" | Rules evaluated across all specs and the extracted code | Static checks over every matching transition | s |

### function

```yaml
kind: function
behavior: Refund amount
function: src/orders/pricing.ts#refundAmount
given:
  order.total: ">= 0"
  order.refunded: "between 0 and order.total"
  requested: ">= 0"
ensures:
  - result >= 0
  - result <= order.total - order.refunded
examples:
  - given: { order: { total: 100, refunded: 30 }, requested: 100 }
    result: 70
```

Generators come from the function's TypeScript parameter types plus the `given` constraints. Each `ensures` line becomes a fast-check property, and each example becomes a test. Later, `decisions:` tables (pricing, permissions) add SMT completeness and overlap checks, and Lean proofs for critical rules.

### entity (prototype scope)

This is what [2.](./2.%20behavior-spec-pivot.md) describes: states, transitions, actors, guards, effects, `atomic`, `idempotent`, rules, concurrency bounds. The checker models **one entity instance** with N concurrent workers per transition. Entities are independent at this scope, so one instance is enough. Cross-entity behavior belongs to **flow**.

### flow

```yaml
kind: flow
behavior: Checkout
uses: [../orders/order.behavior.yaml, ../inventory/stock.behavior.yaml]
entry: src/api/checkout.ts#POST
by: customer
steps:
  - guard: owner
  - transition: Stock.reserve
  - transition: Order.checkout
  - effect: stripe.paymentIntents.create
compensate:
  - if_fails_after: Stock.reserve
    do: Stock.release
rules:
  - always: Stock.reserved implies Order.status in [pending_payment, paid]
```

The checker composes the referenced entity models, sequences the steps, and **injects a failure after every step** to verify the compensations. The extractor checks that the handler calls the steps in the declared order, that the guard dominates the first effect, and that every exception path after `reserve` reaches `release`.

### system

```yaml
kind: system
behavior: Payments
services:
  api:    { flows: [Checkout] }
  worker: { consumes: [stripe_events] }
channels:
  stripe_events: { delivery: at-least-once, ordering: none }
failures: [duplicate-delivery, reorder, crash-between-steps]
rules:
  - eventually: every Payment.succeeded has Order.status = paid
```

This is TLA+'s home territory: many interleavings plus a hostile environment. The built-in checker will eventually hit its limits here, so this scope compiles to **Quint** and runs **Apalache** (or TLC). Conformance links each service's consumers to their flows and checks declared idempotency. Trace validation against real traces comes later.

### policy

```yaml
kind: policy
behavior: Tenant isolation
applies_to: { entities: "*", actors: { trust: untrusted } }
require:
  - every transition: guard tenant_scope
```

### Order of build

**entity** (prototype) → **function** (cheap, high value, reuses fast-check) → **policy** (mostly queries over data we already have) → **flow** → **system** (where the Quint/Apalache backend becomes necessary).

## Open items (non-blocking for the prototype)

1. **Name.** "tsv" collides with *tab-separated values* and probably with existing npm packages. Pick a real name before the first publish. The prototype uses `tsv` internally.
2. **License.** Apache-2.0 (patent grant, common for developer tooling) or MIT (simplest). Current lean: Apache-2.0.
3. **Built-in checker vs. Quint backend at entity scope.** The plan proposes a small built-in explicit-state checker (zero install, millisecond runs, exact counterexamples), plus `tsv export --quint` for interop. Apalache would be required only at the system scope. Rationale: `npx tsv check` must work without a JVM if we want open-source adoption.

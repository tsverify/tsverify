# 1. Proposal: An Evidence Layer for Agent-Written Code

> Status: draft v0.1, **superseded in part by [2. behavior-spec-pivot.md](./2.%20behavior-spec-pivot.md)** (the claims ledger was replaced by agent-written behavior specs). Kept for reference: tool survey, conformance bridges, security table.
> Working name: **`tsv`** (rename later)
> Assumption: "ts" means **TypeScript**. TypeScript is the first target, but the core design doesn't depend on the language.

---

## 0. TL;DR

Agents can now write code faster than humans can review it. Review is the bottleneck. Formal tools (TLA+, Lean, Bend 2) can give strong guarantees, but they check **models and proofs, not your code**, and they are slow to adopt.

`tsv` is a CLI and agent-facing service that sits next to an existing TypeScript codebase and keeps an **evidence ledger**:

1. **Claims**: short, human-ratified statements of intended behavior ("an order is refunded at most once", "every `/admin` route checks the role before writing").
2. **Evidence**: machine-produced support for each claim. It comes from the cheapest engine that can produce it, which might be static analysis, property tests, a model check, or a proof.
3. **Conformance links**: checks that tie each model or proof back to the real code. Without them, formal results only describe a model.
4. **Findings**: violated claims, with a **concrete counterexample turned into a failing TypeScript test**. A coding agent can act on that directly.

Humans review **claims and findings**, which are short and declarative, instead of every line of generated code. The goal is to raise throughput without lowering trust.

---

## 1. Problem

| Today | Consequence |
|---|---|
| Agents write large diffs quickly | Line-by-line human review doesn't scale |
| Tests are often written by the same agent that wrote the code | Tests encode the same misunderstanding as the code ("the agent agrees with itself") |
| Linters and SAST catch syntactic and taint bugs | They miss **design and logic bugs**: races, check-then-act, broken state machines, IDOR, double-spend, retry and idempotency errors |
| Formal methods catch exactly those bugs | They need expertise, separate artifacts, and a lot of time, and they drift out of date with the code |

The gap: there is no lightweight, incremental way to keep **evidence that the intended design holds in the code as written**. There is also no way to tell when that evidence goes stale.

---

## 2. Design principles

1. **Intent comes from outside the code.** If a spec is derived only from the implementation, it inherits the implementation's bugs. Claims must come from intent sources: tickets, PR descriptions, design docs, human statements, or an agent that is **not shown the code**.
2. **Evidence is graded, not binary.** "Proved", "model-checked to depth 12", "property-tested on 10k inputs", and "asserted" are different levels of confidence. The ledger records which one each claim has.
3. **A chain is only as strong as its weakest link.** A Lean proof about a model that doesn't match the code gives roughly zero assurance about the code. *Strength(claim about code) = min(strength of the check on the model, strength of the model↔code link).*
4. **Every failure should be executable.** Every violation should arrive as a reproducible failing test or trace. That is the highest-signal feedback an agent can get.
5. **Cheap first, expensive on demand.** Run fast engines on every change. Run heavy engines only for high-risk code, and asynchronously.
6. **Incremental by default.** Evidence is keyed to content hashes of the symbols it covers (and their dependencies). When the code changes, the evidence goes stale, and only the affected claims re-run.
7. **Sidecar, not rewrite.** No changes to the production code are required. Optional lightweight annotations make the links better.

## 3. What each technology contributes

### Primary formal engines

| Tool | Best at | Weak at | Role in `tsv` |
|---|---|---|---|
| **TLA+** (TLC, Apalache, TLAPS) | Concurrency, distributed protocols, state machines, liveness ("eventually"), retries and idempotency. Proven in industry (AWS, MongoDB, Azure) | Says nothing directly about code. Steep syntax. State explosion | **Design-level model checking** of workflows and async interleavings |
| **Quint** (a TLA-based language with TypeScript-like syntax, checked by Apalache) | Same semantics as TLA+ with syntax that TypeScript developers and LLMs read and write well. Has a simulator and emits **ITF JSON traces** | Younger ecosystem than TLA+ | **The default authoring format for models.** TLA+ is kept as an export/expert path |
| **Lean 4** | Machine-checked proofs of functional correctness. Strong LLM-prover ecosystem. Precedent: AWS **Cedar** (authorization) verified in Lean, plus differential testing against production code | Can't ingest TypeScript directly; translation is a trust gap. Proofs can be expensive | **Proved reference oracles** for pure, critical kernels (authorization decisions, money math, permission lattices, parsers) |
| **Bend 2** (launched Sept 2026: dependent types, checked proofs, affine ownership, GPU execution) | One language for both the executable program and its proof. Massively parallel execution could make **large-scale differential and exhaustive testing** of oracles cheap | Very new. Reported gaps: no tactics or proof search, no incremental compilation, minimal tooling. Secondary sources only so far | **Spike, then evaluate.** Candidate as a faster executable-oracle backend and for GPU-parallel state-space or input-space search. Not on the critical path |

### Supporting engines (fast tiers)

| Tool | Role |
|---|---|
| TypeScript compiler API / ts-morph | Symbol graph, call graph, hashing, anchoring claims to code |
| **fast-check** | Property-based tests generated from pre/post-condition and invariant claims, with shrinking |
| **CodeQL / Semgrep** | Security claims as queries: taint (input → SQL, exec, fs, redirect, SSRF), authorization dominance ("the check happens before the write on every path") |
| Stryker (mutation testing) | Measures whether the evidence actually detects bugs. Used for calibration |
| Dafny *(optional)* | Verified code that compiles to JavaScript, for kernels where you want the shipped code to be the verified code |
| Z3 / SMT | Under the hood: bounded checks of local arithmetic and branch conditions |

### 4.1 Claims (the intent layer)

A claim is a small, reviewable record:

```yaml
# .tsv/claims/orders.yaml
- id: refund.at-most-once
  statement: An order is refunded at most once, even under concurrent refund requests.
  kind: invariant            # invariant | pre-post | temporal | security-policy | non-functional
  origin: intent             # intent | inferred-from-code | imported (e.g. threat model)
  source: "PR #142 description; ticket PAY-88"
  ratified: { by: "@owner", at: 2026-11-21 }   # unratified claims are reported but never block
  risk: high                 # drives which tiers run
  scope:
    - symbol: src/orders/refund.ts#refundOrder
    - symbol: src/payments/stripe.ts#issueRefund
```

**Two-way derivation** (a key idea for agent-written code):
- Agent A writes claims from the **intent sources only**, without seeing the code.
- Agent B writes claims from the **code only** ("what does this actually guarantee?").
- `tsv` diffs the two sets. Each mismatch is either a missing claim, a missing behavior, or a bug, and each one goes to a human as a one-line question. This targets the "agent agrees with itself" failure mode.

### 4.2 Evidence engines (tiers)

| Tier | Budget | Runs | Example output |
|---|---|---|---|
| **T0 Static** | seconds | every save / commit | "Write at `admin.ts:88` is reachable without `requireRole`" |
| **T1 Properties** | seconds–minutes | every commit | fast-check counterexample for `applyDiscount(price, pct)` returning a negative value |
| **T2 Models** | minutes | PRs touching scoped symbols | Quint/Apalache: 2 workers interleave → `refundsIssued = 2` |
| **T3 Proofs** | async, hours | high-risk claims, nightly | Lean: `authorize` oracle proved monotone in the role lattice |

The scheduler picks tiers from `risk`, from what changed, and from a time budget (`tsv check --budget 90s`).

### 4.3 Conformance bridges (where the value comes from)

Formal results only count toward a claim about code if a bridge links them to the code. Planned bridges, in order of build priority:

1. **Anchors.** Optional comments or JSDoc tags map code regions to model actions:
   `// @tsv action Refund.check`. The indexer verifies that anchors exist, flags when anchored code changes (stale evidence), and flags model actions that have no anchor (unmodeled code).
2. **Counterexample → test replay.** A model violation (an ITF trace) is compiled into a deterministic TypeScript test. A controllable scheduler and fakes force the same interleaving against the real functions. If the test fails, the bug is confirmed in the real code, not just in the model. If it passes, the model is wrong, which is itself a finding.
3. **Model-based test generation.** The Quint simulator produces many valid behaviors, including adversarial interleavings. Each one is replayed against the implementation, which is asserted to match the model's state.
4. **Trace validation.** Instrumented test and staging runs emit action events. `tsv` checks that each recorded trace is a legal behavior of the model (MongoDB's TLA+ trace-checking is the precedent). This catches code drifting away from the design.
5. **Differential oracles.** A Lean-proved (or Bend 2) reference implementation of a pure kernel is executed and compared with the TypeScript implementation on millions of generated inputs (the Cedar pattern). This avoids translating TypeScript into Lean. The proof covers the oracle, and differential testing links the oracle to the code.

### 4.4 Evidence ledger

```yaml
# .tsv/ledger/refund.at-most-once.yaml   (machine-written, committed)
claim: refund.at-most-once
code_hash: sha256:9f1c…            # hash of scoped symbols + transitive deps
status: violated                    # proved | holds-bounded | holds-sampled | violated | stale | unverified
strength: L3-bounded                # see ladder below
evidence:
  - engine: quint+apalache
    model: .tsv/models/refund.qnt
    bounds: { steps: 12, workers: 2 }
    result: violated
    counterexample: .tsv/cex/refund.at-most-once.itf.json
  - engine: cex-replay
    test: .tsv/generated/refund.at-most-once.cex.test.ts
    result: failed (bug confirmed in implementation)
```

**Strength ladder:**
`L0` asserted → `L1` example-tested → `L2` property-tested → `L3` bounded model-checked *and* conformance-linked → `L4` proved *and* conformance-linked.

A proof with no bridge to the code is capped at the strength of the code↔model link.

### 4.5 Interfaces

- **CLI:** `tsv init`, `tsv claims propose`, `tsv check [--budget]`, `tsv explain <claim>`, `tsv replay <cex>`.
- **CI:** a GitHub check plus **SARIF** output, so findings appear inline in code scanning. A PR comment summarizes the claim diff and evidence diff ("3 claims strengthened, 1 went stale, 1 violated").
- **MCP server:** lets coding agents ask "which claims cover the file I'm editing?" and "run T0–T2 for this symbol". Agents get counterexamples as failing tests in their loop, before a human ever sees the PR.

## 5. Accompanying files layout

```
repo/
├─ src/…                         # untouched production code (optional @tsv anchors)
└─ .tsv/
   ├─ config.yaml                # tiers, budgets, engines, risk defaults
   ├─ claims/*.yaml              # human-ratified intent (reviewed in PRs)
   ├─ models/*.qnt               # Quint models (or *.tla)
   ├─ proofs/                    # Lean 4 project (lakefile) for T3 oracles/proofs
   ├─ properties/*.prop.ts       # generated/handwritten fast-check properties
   ├─ queries/                   # CodeQL / Semgrep rules for security claims
   ├─ generated/                 # replay tests, harnesses (regenerable, may be gitignored)
   ├─ cex/                       # counterexample traces (ITF JSON)
   └─ ledger/*.yaml              # evidence ledger (committed → auditable history)
```

What humans review in a PR: `claims/` diffs, and the ledger summary. Everything else can be produced by machines.

## 6. Walkthrough: the double-refund bug

**Code (written by an agent, looks fine, and its unit tests pass):**

```ts
export async function refundOrder(id: string) {
  const order = await db.orders.get(id);           // @tsv action Refund.check
  if (order.status !== "paid") throw new Error("not refundable");
  await stripe.refunds.create({ charge: order.chargeId });  // @tsv action Refund.refund
  await db.orders.update(id, { status: "refunded" });
}
```

**Model (proposed by an agent from the claim plus the anchors, ~25 lines of Quint; syntax is illustrative):**

```quint
module Refund {
  type Pc = Idle | Checked | Done
  val WORKERS = Set(1, 2)
  var status: str
  var refundsIssued: int
  var pc: int -> Pc

  action init = all { status' = "paid", refundsIssued' = 0, pc' = WORKERS.mapBy(_ => Idle) }

  action check(w: int): bool = all {
    pc.get(w) == Idle, status == "paid",
    pc' = pc.set(w, Checked), status' = status, refundsIssued' = refundsIssued,
  }
  action refund(w: int): bool = all {
    pc.get(w) == Checked,
    refundsIssued' = refundsIssued + 1, status' = "refunded", pc' = pc.set(w, Done),
  }
  action step = { nondet w = WORKERS.oneOf()  any { check(w), refund(w) } }

  val NoDoubleRefund = refundsIssued <= 1      // ← claim refund.at-most-once
}
```

**Result:**
1. Apalache finds the trace `check(1) → check(2) → refund(1) → refund(2)`, which ends with `refundsIssued = 2`.
2. `tsv` turns the trace into `refund.at-most-once.cex.test.ts`, which forces both calls past the `get` before either one updates. The test **fails against the real code**, so the bug is confirmed.
3. A finding appears in the PR and through MCP. The agent fixes it with a conditional update (`UPDATE … WHERE status='paid'`) plus a Stripe idempotency key, and updates the model and anchors. The re-check holds to depth 12, so the claim reaches `L3`.

Linters, SAST, and the agent's own unit tests would not catch this bug, and design-level checking catches it cheaply.

## 7. Running quickly on existing codebases

1. **`tsv init` with zero specs.** It indexes the repo and ranks **hotspots** using heuristics:
   - status enums combined with `switch` or `if` on status (implicit state machines)
   - `await`-separated read-then-write against a DB or external API (check-then-act)
   - money and quantity arithmetic
   - route handlers and authorization helpers
   - retries, queues, webhooks, cron jobs (idempotency)
   - crypto and secrets usage
2. **Inferred claims.** It proposes claims for the top N hotspots, marked `origin: inferred` and unratified. These are reported but never block, so the tool shows value in the first session.
3. **Progressive ratification.** Humans accept, edit, or reject claims in batches, and only ratified claims can block CI.
4. **Incremental cache.** Evidence is keyed by symbol hash and dependency closure, so a typical PR re-runs only the claims whose scope changed.
5. **Budgets.** A hard time budget per run. Expensive tiers degrade gracefully to "not run (budget)" instead of blocking.

## 8. Security auditing

| Bug class | Engine | Example claim |
|---|---|---|
| Injection, SSRF, path traversal, open redirect | T0 CodeQL/Semgrep taint | "No request-derived value reaches `child_process` or a raw SQL string" |
| Missing or misordered authorization | T0 dominance query | "On every path in `/admin/**` handlers, `requireRole('admin')` runs before any write" |
| IDOR / tenant isolation | T0 + T1 | "Every query on `invoices` is filtered by `session.tenantId`." Property: a generated cross-tenant ID is always denied |
| TOCTOU, double-spend, replay, broken idempotency | T2 models + replay | "A webhook processed twice has the same effect as once" |
| Authorization policy logic | T3 Lean oracle + differential testing | "Deny overrides allow"; "adding a role never removes a permission" |
| Secrets and crypto misuse | T0 rules | "Tokens are compared in constant time"; "no secrets in logs" |

Threat models (STRIDE or a simple list) can be imported as `origin: imported` claims, so every threat either has evidence or is visibly unaddressed.

## 9. Phased plan

**Phase 1: MVP (prove the loop works)**
- TypeScript (Node backend) only. `tsv` itself is written in TypeScript (ts-morph); Quint installs from npm, and Apalache needs a JVM.
- Claims format, ledger, hashing and staleness.
- Engines: T0 (Semgrep plus a few CodeQL queries), T1 (fast-check from pre/post claims), T2 (Quint/Apalache for one pattern: **check-then-act / state machines**).
- Bridges: anchors plus **counterexample → test replay** (the most compelling demo).
- CLI and SARIF output.
- **Benchmark:** a small set of sample repos with seeded design bugs (double-refund, IDOR, missing authorization, broken state transition, non-idempotent webhook). Measure detection rate, false positives, and wall-clock time.

**Phase 2: Agent-native**
- MCP server, two-way claim derivation, hotspot discovery on real open-source repos.
- Model-based test generation and trace validation.
- PR claim and evidence diff comments.

**Phase 3: Deep assurance**
- Lean 4 oracles and proofs for pure kernels, plus differential testing.
- **Bend 2 spike:** compare it with Lean on (a) LLM proof success rate, (b) oracle execution throughput for differential testing, (c) tooling maturity. Decide whether to adopt, defer, or drop.
- Optional Dafny path for verified kernels that compile to JavaScript.

## 10. Risks and limits

- **Model↔code gap.** This is the main risk. It is handled by the bridges and the strength cap, not hidden.
- **Spec quality.** A wrong claim produces wrong confidence. Mitigations: intent-sourced claims, two-way derivation, human ratification, and mutation testing to check that the evidence actually detects bugs.
- **Bounded ≠ proved.** Model checking is exhaustive only within its bounds. The ledger always records the bounds.
- **Replay fidelity.** Forcing interleavings needs injectable I/O (db, http, clock). Codebases that aren't built for that need adapters, which may limit Phase 1 to repos with some dependency-injection seams.
- **Toolchain weight.** Using a JVM (Apalache), Lean, and CodeQL together is a lot. Ship a container image and let users enable engines one at a time.
- **Bend 2 maturity.** It is new, its tooling is thin, and so far only secondary sources describe it. It is deliberately kept off the critical path.
- **Alert fatigue.** Unratified claims never block, and every finding must carry a reproducible counterexample, or it is downgraded to a warning.

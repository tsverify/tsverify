# @tsv/testgen

Generates the vitest files `tsv test` writes and runs. Depends only on `@tsv/ir` (doc 6 §2): it
never imports `@tsv/runtime` in `src/` (only its tests do, as a devDependency); the **generated
code** imports it at test time. Pure: data in, files (as strings) out, deterministic.

```ts
import { generate } from "@tsv/testgen";

const { files, skipped, tests } = generate({
  spec,       // spec model; `file` and locations relative to the project root
  code,       // the extractor's code model for the same spec
  findings,   // `tsv check` findings; those with a `trace` become replay tests
  outDir: ".tsv/generated/order-lifecycle", // project-relative, used for import paths
});
// files:   { path (relative to outDir), content }[]
// skipped: info findings (`unanalyzable:<behavior>:testgen:…`) saying what was not generated
// tests:   one descriptor per generated test(…), so the CLI can map vitest results back
```

## Generated files

Every file starts with `// Generated by tsv — do not edit.` and names the spec and the source
transition or finding (JSON sidecars carry the same text in `$comment`). Every test file has the
same prelude (the shape of `packages/runtime/test/generated-shape.test.ts`): fakes as top-level
consts (`instrument.store` for storage clients, `instrument.effects` for the others, configured
from all `CodeSites` like the runtime's `storeConfigFromCode` / `effectsConfigFromCode`), one
`vi.mock` per `bindings.clients` module (path relative to the generated file), the impls imported
dynamically, and the fixtures (`ID`, `ENTITY`, `ACTORS`).

| File | One test per | Asserts |
|---|---|---|
| `paths.test.ts` | linked transition × allowed `from` state | stored state is `to`; each exactly-once effect called once (at-least-once / idempotent: ≥ 1); **no other effect call** |
| `forbidden.test.ts` | linked transition × state outside `from` | stored state unchanged; no declared effect fired (throwing is allowed) |
| `guards.test.ts` | linked transition × actor with a fixture not in `by` | stored state unchanged; no declared effect fired |
| `replay-<n>.test.ts` + `replay-<n>.json` | finding with a counterexample (spec or code model) | the violated property, after replaying the trace's interleaving |

A transition is drivable when the code model has its write (`sites.specTransition`) with an
`invocation` and a `storage` site under `assign` persistence. The impl is called as the first actor
in `by` that has a fixture (or with no actor when the impl takes none), with `fixtures.args[t]`
(`$id` / `$actor` substituted) or else arguments built from the `InvocationShape`. State tests call
the impl outside any scheduler worker, so every gate passes straight through.

### Replays

The sidecar holds the trace and the `CodeSites` subset `mappingFromCode` reads. The test seeds the
entity in `plan.seedStatus`, spawns one worker per trace worker (each calls its transition's impl),
`tryPlay`s the schedule, `drain`s, evaluates the property in code terms and calls `replayResult`.

- **Planning.** The sidecar holds the trace unchanged. When the runtime's default fast-forward
  leaves something drivable to replay, the test plans with the default (B3, B6). Otherwise it
  passes `{ replayFrom: i }`, the step after the last one it cannot drive: an all-atomic trace
  (B4's duplicate webhook) replays from the initial state (`replayFrom: 1`); a step on an unlinked
  transition (B1's `reopenOrder`, step 3) is seeded instead of replayed (`replayFrom: 4`).
  `src/replay-plan.ts` mirrors the runtime's rules; `test/runtime-cross-check.test.ts` runs the
  real runtime (a devDependency) on the generated sidecars and plan options to keep the two in
  step, along with the fake configs `src/context.ts` derives like `storeConfigFromCode`.
- **Properties.** `effect-multiplicity` and `always` / `never` rules over status checks and effect
  counts are evaluated (`effects[gate]` = fast-forwarded prefix + calls in the replay; `status` =
  the stored entity). Anything else (`eventually`, liveness, structural properties) gives an
  **inconclusive** replay: it still runs, calls `replayResult(outcome, undefined)` (verdict
  `inconclusive`) and passes.

### Verdict channel

Each replay test sets `task.meta.tsvReplay` before its assertion; `tsv test` reads it from
vitest's `TestCase.meta()`:

```ts
tsvReplay: ReplayResult & {          // { verdict, followed, violated?, divergence? } from @tsv/runtime
  status: unknown;                   // stored state after drain
  effects: Record<string, number>;   // calls per effect gate, seeded prefix included
}
```

`confirmed` and `confirmed-divergent` fail the test (`expect(result.violated, "<verdict>: the real
code violates <property>…").toBe(false)`); `replay-disagrees` and `inconclusive` (no `violated`)
pass. A replay test that fails
without `tsvReplay` could not run at all.

## Skipped (info findings)

No `fixtures`; `memory` persistence (no fakes or replay support yet) or another non-`assign`
persistence; a transition without `impl`, linked write, invocation shape or storage site; no actor
fixture for a transition whose impl takes an actor; guard tests for impls that take no actor; a
counterexample with nothing drivable left to replay.

## How `tsv test` uses it

`tsv test` writes each spec's files to `<project>/.tsv/generated/<spec-slug>/` (deleted first),
runs them in-process with vitest (`config: false`, `@tsv/runtime` aliased to tsv's own copy, caches
in `.tsv/cache/`) and maps the results to `generated-test-failed`, `replay-confirmed` and
`replay-disagrees` findings. The files are **kept** after the run so a failure can be read and
debugged; add `.tsv/` to `.gitignore`. There is no `--keep` flag: keeping is the only behavior.
